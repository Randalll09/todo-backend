단계

00

판 깔기

반나절
함정

synchronize: true는 편하지만 엔티티에서 컬럼을 지우면 DB 컬럼도 데이터째 날아갑니다. Phase 6에서 마이그레이션으로 갈아탄 뒤에는 다시는 켜지 마세요.

학습 포인트

NestJS가 왜 모듈과 프로바이더로 쪼개져 있는지. 여기서 DI 컨테이너 감각을 잡아두면 이후 모든 단계가 수월합니다.

01

인증 — 회원가입과 로그인

3~4일

왜 여기가 먼저인가. 투두도 이미지도 친구도 전부 “누구의 것이냐”에 달려 있습니다. 인증을 나중에 붙이면 앞서 짠 코드를 거의 다 고치게 돼요. 여기가 전체의 기둥입니다.

함정 둘

비밀번호 유출 — 응답에 passwordHash가 그대로 실려 나갑니다. 엔티티에 @Exclude()를 달고 ClassSerializerInterceptor를 전역 등록하세요.

친절한 에러 메시지 — “가입되지 않은 이메일”과 “비밀번호가 틀렸습니다”를 구분해 주면, 공격자에게 어떤 이메일이 가입돼 있는지 알려주는 셈입니다. 로그인 실패는 한 가지 메시지로.

학습 포인트

Middleware / Guard / Interceptor / Pipe / Filter가 각각 언제 실행되는지. NestJS를 이해했다는 건 사실상 이 순서를 안다는 뜻입니다.

Refresh token은 지금 하지 마세요. access token 하나로 충분하고, Phase 6에서 제대로 붙입니다.

02

투두 CRUD

2~3일
함정

403 대신 404를 주세요. 남의 투두에 403을 반환하면 “그 id는 존재한다”는 사실이 새어 나갑니다. 권한이 없으면 애초에 없는 것처럼 취급하는 게 기본입니다.

N+1 쿼리 — 목록 조회에 습관적으로 relations: ['owner']를 붙이면 금방 터집니다. 필요한 컬럼만 QueryBuilder로 가져오세요.

학습 포인트

서비스 레이어는 HTTP를 몰라야 합니다. 컨트롤러는 요청/응답 변환만, 규칙은 전부 서비스에. 이 선을 지키면 Phase 5의 권한 로직이 훨씬 깔끔해집니다.

03

이미지 업로드

2~3일
함정

고아 파일. presign을 받아 업로드까지 했는데 투두 저장이 실패하면, 스토리지에만 파일이 남아 영원히 요금을 냅니다. status: pending → confirmed 컬럼을 두고 미확정 파일을 주기적으로 정리하세요. 이 문제를 직접 겪어보는 게 이 단계의 핵심입니다.

그리고 버킷을 public으로 열어두지 마세요. 한 번 유출된 URL은 회수할 수 없습니다.

학습 포인트

“위치(key)는 DB에, 실체는 스토리지에”가 왜 표준인지. presigned 방식은 파일이 서버 메모리와 대역폭을 아예 거치지 않기 때문에, 서버 사양과 무관하게 대용량을 감당합니다.

04

친구 관계

3~4일

설계가 가장 재밌는 구간입니다. 여기서 처음으로 “두 사용자 사이의 관계”라는, 소유 관계가 아닌 데이터를 다루게 됩니다.

함정

서비스 코드 검증만 믿지 마세요. 사용자가 “친구 요청” 버튼을 두 번 빠르게 누르면 두 요청이 동시에 검사를 통과합니다. 한 행 방식이라면 UNIQUE (LEAST(requester_id, addressee_id), GREATEST(...)) 같은 제약을 DB에 직접 걸어야 막힙니다.

엣지 케이스 목록을 미리 적어두세요 — 자기 자신에게 요청, 이미 친구인데 재요청, A가 B에게 요청한 상태에서 B가 A에게 요청(→ 자동 수락이 자연스럽습니다), 차단된 상대에게 요청.

학습 포인트

트랜잭션. 수락 처리에서 상태 변경과 부수 작업(알림 생성 등)이 함께 성공하거나 함께 실패해야 하는 이유를 몸으로 익히는 자리입니다.

05

친구의 투두 보기

2일

권한 로직의 시험대. 지금까지는 “내 것이냐 아니냐” 둘 중 하나였지만, 여기서 본인 · 친구 · 남 세 갈래가 됩니다.

함정

친구 목록을 가져와 루프를 돌며 투두를 조회하면 친구 30명에 쿼리 31번입니다. JOIN 한 번으로 끝내세요.

visibility 필터를 컨트롤러에서 하지 마세요. 엔드포인트가 늘어나면 언젠가 한 곳에서 빠뜨립니다. 리포지토리 레벨에서 강제하는 편이 안전합니다.

학습 포인트

인증(누구인가)과 인가(무엇을 할 수 있나)는 완전히 다른 문제라는 것. Phase 1에서 만든 Guard는 전자만 해결했을 뿐입니다.

06

실무처럼 다듬기

2~3일
함정

테스트를 개발 DB에 돌려서 데이터를 통째로 날리는 일이 흔합니다. 테스트용 Postgres 컨테이너를 따로 띄우세요.

학습 포인트

E2E 하나를 제대로 짜두면 이후 리팩터링이 두렵지 않아집니다. 유닛 테스트를 100개 짜는 것보다 이 한 줄기가 먼저입니다.

07

배포

1~2일
함정

Tauri 앱의 오리진은 웹이 아닙니다. tauri://localhost(윈도우에서는 http://tauri.localhost) 형태라 일반적인 CORS 설정으로는 막힙니다. 다음 단계에서 plugin-http를 쓰면 Rust가 요청을 보내기 때문에 CORS 자체가 사라집니다 — 그쪽이 훨씬 편합니다.

08

Tauri 클라이언트 붙이기

1~2주
함정

토큰을 localStorage에 넣지 마세요. 웹에서는 그럭저럭 통하지만 데스크톱 앱은 사용자 PC에 파일로 남습니다. 다른 프로그램이 읽을 수 있어요.

오프라인 동기화는 욕심내지 마세요. 충돌 해결까지 들어가면 난이도가 백엔드 전체보다 높아집니다.

학습 포인트

Phase 3에서 presigned 방식으로 만들어 둔 게 여기서 값을 합니다. 클라이언트가 바뀌어도 업로드 로직은 그대로예요 — 나중에 모바일 앱을 붙일 때도 마찬가지입니다.
